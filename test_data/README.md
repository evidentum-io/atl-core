# Test Data

This directory contains test vectors and sample data for atl-core testing.

## Structure

```
test_data/
├── vectors/           # Frozen test vectors with recorded provenance
│   ├── jcs/          # RFC 8785 JSON Canonicalization Scheme
│   │   └── cases.json
│   ├── merkle/       # RFC 6962 / RFC 9162 Merkle tree operations
│   │   └── trees.json
│   └── atl/          # ATL-specific constructions
│       ├── leaf_composition.json
│       └── super_tree.json
├── implementation_only/   # NOT vectors: pins on atl-core's own arithmetic
│   └── genesis_chain_leaf.json
└── receipts/         # Sample receipt files (*.atl)
    ├── valid/        # Valid receipts that should pass verification
    │   ├── minimal.atl
    │   ├── with_metadata.atl
    │   └── with_anchors.atl
    └── invalid/      # Invalid receipts for negative testing
        ├── unsupported_version.atl
        ├── invalid_hash_format.atl
        └── malformed_json.atl
```

## Test Vectors

Every expected value under `vectors/` is **frozen** and carries its **origin**. Nothing
there was produced by running `atl-core`.

That rule is the whole point. A vector generated by the implementation it tests proves
nothing: it freezes that implementation's bugs and confirms them forever. ATL's promise to
a relying party is "check it yourself, without trusting us", and that promise is only real
if a third party can check their own implementation against these files without possessing
or running ours.

### Origins

| Origin                     | Meaning                                                                                                   |
|----------------------------|-----------------------------------------------------------------------------------------------------------|
| `rfc6962-published`        | Certificate Transparency reference vector set, additionally re-derived from RFC 6962 Section 2.1 independently |
| `rfc6962-symbolic`         | Structure stated in RFC 6962 Section 2.1.3 itself, as node labels of the 7-leaf diagram                     |
| `rfc6962-derived`          | Computed from the RFC 6962 Section 2.1 / 2.1.1 / 2.1.2 algorithm text by an independent implementation      |
| `rfc8785-published`        | Verbatim from RFC 8785 (Section 3.2.2, Section 3.2.3, Appendix B Table 1)                                   |
| `rfc8785-derived`          | Written from RFC 8785 rule text; integer-only, so decidable by inspection                                  |
| `atl-spec-derived`         | Hand-derived from a named clause of `atl-protocol-ietf.md` with an independent SHA-256                     |

Neither RFC 6962 nor RFC 9162 ships a table of hexadecimal test vectors. RFC 6962
Section 2.1.3 does state its 7-leaf worked example symbolically (audit paths and
consistency proofs written as node labels `a`..`l`), and that statement is the one piece
of proof structure the RFC document itself pins down; `merkle/trees.json` binds those
labels to concrete hashes and `tests/rfc_vectors.rs` asserts them literally.

### `merkle/trees.json`

RFC 6962 / RFC 9162 tree geometry over the eight published CT reference records:

- leaf hashes and the empty-tree root
- roots for tree sizes 0 through 8, including the odd and non-power-of-two sizes where
  the RFC 6962 split rule is not a simple halving
- inclusion proofs for **every** leaf position at **every** tree size 1 through 8
- consistency proofs for **every** size pair `1 <= m <= n <= 8`
- the RFC 6962 Section 2.1.3 node-label table

Note: `atl-core`'s Merkle functions consume leaf *hashes*, not records. Feed
`records[].leaf_hash`, not `records[].data_hex`.

### `atl/leaf_composition.json`

The ATL-specific leaf: `MetadataHash = SHA256(JCS(metadata))` and
`LeafHash = SHA256(0x00 || PayloadHash || MetadataHash)`, with the canonical JSON byte
string recorded for every case so the chain can be checked by reading. Also holds the
genesis chain leaf (`compute_genesis_leaf_hash`), flagged because that construction has no
first source in the protocol specification.

### `atl/super_tree.json`

Super Roots, `genesis_super_root`, Super-Tree inclusion and consistency-to-origin proofs.
The Super-Tree leaves are the published CT roots, so the whole structure is anchored to
externally known inputs. The file also records why a Data Tree root is used *directly* as
a Super-Tree leaf hash rather than re-hashed as `SHA256(0x00 || root_hash)`.

### `implementation_only/` — deliberately not vectors

`compute_genesis_leaf_hash` and its `"ATL-CHAIN-v1"` domain are public API of `atl-core`,
but the construction appears nowhere in `atl-protocol-ietf.md`. An independent SHA-256 can
confirm the *arithmetic* of such a value; nothing can confirm the *contract*. A third-party
implementer has no document to implement it from, so matching these hashes would only mean
they copied us — which is the same failure as the `"root": "computed"` placeholders this
work replaced, merely labelled more honestly.

Such values are therefore kept **outside `vectors/`**, in `implementation_only/`, and the
file says so on its first line. They are regression pins: they catch an accidental change
to a public function, and they ground no conformance claim.

`tests/rfc_vectors.rs` asserts this boundary — a value whose `origin` is not one of the
externally-grounded kinds above cannot sit under `vectors/`.

To promote such a file into `vectors/`: get the construction into the protocol
specification, then re-derive the values from that clause. Failing that, mark the API
non-protocol in its own doc comment.

### `jcs/cases.json`

RFC 8785 canonicalization cases and the full Appendix B number-serialization table.

Cases carry a `conformance` marker. `known_divergence` means `atl-core` does **not**
currently produce the RFC value; the RFC value stays in `expected`, unchanged and
deliberately not adjusted to match.

Such a case also carries `atl_core_actual`, which pins the wrong output `atl-core` emits
today. This is the one field in the whole vector set taken from the implementation, and it
exists so the test can distinguish two events instead of one:

- output becomes the RFC value → the bug is fixed; the marker, the pin and the
  `known_divergences` entry must all be removed;
- output becomes anything else → a **new** bug replaced the documented one.

Asserting only "differs from the RFC value" would have accepted any wrong answer at all.

`known_divergences` in the file analyses whatever causes are currently open. **It is empty:
every case in the file is `pass`.** The three causes it used to describe — no exponential
notation, shortest-digit ties broken away from zero, and a JSON number literal parsed into
the double next to the correct one — are fixed; see CHANGELOG.md.

The marker vocabulary is documented rather than deleted, because a future divergence must
be recorded this way, with the RFC value left untouched, and never by editing `expected`.
`tests/rfc_vectors.rs` keeps the two sides consistent in both directions: a marker with no
description fails, and a description no case claims fails too, so a repair cannot leave
prose behind describing a defect that no longer exists.

## Receipt Samples

### Valid Receipts

- `minimal.atl`: Minimal valid receipt (single leaf, no metadata)
- `with_metadata.atl`: Receipt with rich metadata
- `with_anchors.atl`: Receipt with external timestamp anchors (RFC 3161, Bitcoin OTS)

### Invalid Receipts

- `unsupported_version.atl`: Receipt with unsupported spec_version
- `invalid_hash_format.atl`: Receipt with malformed hash string
- `malformed_json.atl`: Receipt with invalid JSON syntax

## Usage

These test vectors are used in:
- Conformance tests against frozen vectors (`tests/rfc_vectors.rs`)
- Unit tests (in `src/core/*.rs`)
- Integration tests (`tests/integration.rs`)
- Property-based tests (`tests/proptests.rs`)

## Maintenance

When updating the ATL Protocol specification:
1. Update test vectors to match the new spec
2. Add new test cases for edge cases
3. Keep invalid samples to ensure error handling
4. Document any breaking changes

Rules for `vectors/`:

1. **Never** regenerate an expected value by running `atl-core`. Derive it from the RFC or
   from the specification clause, using an implementation that is not this one.
2. Every new entry carries an `origin`, and every value whose origin is a specification
   carries the clause it came from and the formula used.
3. If `atl-core` disagrees with a frozen value, the frozen value is not the thing to
   change. Investigate; if the specification is right, fix the code.
4. A value that can only be justified by pointing at `atl-core` does not belong under
   `vectors/`. Put it in `implementation_only/` and say why on the file's first line.
